## R1 · 2026-09-20 20:26 UTC · proposal #13 · `gov/improve.py`

**the code sandbox is a subprocess with no filesystem, user or resource isolation (gov/improve.py:206)**

- **Advantage.** The sandbox subprocess in gov/improve.py:206 currently has no resource isolation, so a runaway or hostile suite can consume unbounded CPU, memory, processes, file descriptors, or disk. The patch adds a preexec_fn that, before exec, sets RLIMIT_CPU to SUITE_TIMEOUT_S, RLIMIT_AS to 2 GiB, RLIMIT_NPROC to 256, RLIMIT_FSIZE to 512 MiB, RLIMIT_NOFILE to 256, and calls os.setsid() to detach the child into its own session/process group. This bounds the blast of a misbehaving suite and makes timeout enforcement more robust (CPU limit backs up the wall-clock timeout). Evidence that it does not break existing behavior: the patched copy shows no new failure in any suite — governor 16/16, work 23/23, settlement 235/236, mechanic 210/212, identical to the before counts.
- **Risk.** Concrete regressions: (1) RLIMIT_AS of 2 GiB may be too low for suites that legitimately allocate large buffers or load big fixtures, causing MemoryError in settlement or mechanic suites that currently pass; (2) RLIMIT_NPROC 256 is per-UID, not per-process, so on a busy host the limit can be hit by unrelated processes and cause fork failures in the suite; (3) RLIMIT_FSIZE 512 MiB silently truncates or SIGXFSZ-kills any suite writing a larger artifact; (4) RLIMIT_NOFILE 256 may break suites that open many files or sockets; (5) preexec_fn is not thread-safe and is documented as unsafe in multi-threaded parents — if improve.py is ever called from a threaded context, the child can deadlock before exec; (6) os.setsid() in preexec_fn can fail with EPERM if the child is already a process-group leader, aborting the run; (7) RLIMIT_CPU is a soft/hard pair set to the same value, so the child gets SIGXCPU at SUITE_TIMEOUT_S and SIGKILL shortly after, which may turn a slow-but-passing suite into a failure. The suite counts are unchanged on the patched copy, but that only proves the current suites stay under these limits — it does not prove the limits are safe for future or larger suites.
- **Blast radius.** Only the code-sandbox subprocess spawned in gov/improve.py around line 206 (the loop over `want` running each suite via subprocess.run). Callers of that function — the governor/improve entry point and anything that invokes it — are affected only insofar as suite results change. No other subprocess in the repo is touched. Records affected: the suite result records (passed/total per suite) written by improve.py, and any downstream governor/work/settlement/mechanic records derived from those results. The four suites themselves (governor, work, settlement, mechanic) are the direct blast surface.
- **Detection.** A regression would show as a drop in the passed/total counts for one or more suites in the improve.py output — e.g. settlement falling below 235/236 or mechanic below 210/212 — or as a suite erroring out with MemoryError, OSError (EAGAIN/EMFILE/EPERM), SIGXCPU, or SIGXFSZ in the captured stdout/stderr that improve.py concatenates into `text`. Because improve.py parses the last `_PASSED` match, a suite killed before printing its summary would be recorded as 0/0, which is the clearest detection signal. The governor suite (16/16) is the first place a preexec_fn/setsid failure would surface, since it exercises the improve path.
- **Undo.** Reverse the diff: remove `import resource`, remove the `_limits` function, and remove the `preexec_fn=_limits` argument from the subprocess.run call, restoring the original single-line call. Because the change is confined to one call site and one import, revert is a two-hunk patch with no data migration; the next improve.py run will simply spawn the sandbox as before.
- **Alternatives.** Alternatives considered: (a) use `subprocess.run(..., timeout=...)` alone — already present, but it only kills on wall-clock and does not bound memory, processes, or file size, so it does not address the finding; (b) use a container/namespace (unshare, bubblewrap, cgroups) for real isolation — stronger, but requires privileges and platform support not guaranteed in the Phoenix environment, and is a much larger change than this finding warrants; (c) use `resource` limits set in the parent before fork via a wrapper script — equivalent effect but adds a file and indirection; (d) use `preexec_fn` with only setsid and rely on the existing timeout — leaves memory/process/fd unbounded. The chosen patch is the minimal in-process way to add resource isolation without new dependencies, which is why it was preferred over (b) and (c).

## R2 · 2026-09-20 20:33 UTC · proposal #14 · `gov/improve_page.py`

**a credential (`console_token`) is kept in browser storage (gov/improve_page.py:62)**

- **Advantage.** Removes the persistent `console_token` credential from browser storage: the patched script no longer calls `localStorage.getItem('console_token')` or `localStorage.setItem('console_token', ...)`, so the token lives only in the in-memory `TOKEN` variable for the current session. This directly closes the finding at gov/improve_page.py:62 (credential kept in browser storage) and is known to be safe from the suite evidence: governor 16/16, work 23/23, settlement 235/236, mechanic 210/212 after the patch, identical to the before counts, so no suite regressed.
- **Risk.** The token is no longer persisted, so a page reload or navigation loses it and the operator must re-enter it; any workflow that assumed the token survived a refresh will now fail until re-entered. The `DOMContentLoaded` handler still writes `TOKEN` (now always empty) into `$('tok').value`, so on load the field is blank rather than pre-filled. The alert text changed from 'token saved in this browser' to 'token held in memory for this session only', which any test or user expecting the old string would notice. There is no evidence in the suites that token persistence was exercised, so this behavioral change is untested by the provided counts.
- **Blast radius.** Only the page generated by gov/improve_page.py and its inline script are affected; the `console_token` key is no longer read from or written to localStorage, so any other page or tool that relied on reading `console_token` from the same origin's localStorage would stop finding it. Callers are the browser session using this page and the `$('tok')` input and `$('savetok')` button handlers; no server-side records or other suites are touched.
- **Detection.** A failure would show as the token field being empty after reload on the improve_page page, or as an operator being unable to perform token-gated actions after a refresh. In suites, a regression would appear as a drop in governor, work, settlement, or mechanic pass counts from the recorded after-state (16/16, 23/23, 235/236, 210/212); the provided evidence shows no such drop.
- **Undo.** Revert the diff: restore `let TOKEN='';try{TOKEN=localStorage.getItem('console_token')||''}catch(e){}` and the `localStorage.setItem('console_token',TOKEN)` call in the `savetok` handler, and restore the original alert text. Because the change is confined to gov/improve_page.py, undo is a single-file revert with no migration.
- **Alternatives.** Keep localStorage but encrypt or scope the token, or move it to a session cookie or in-memory-only with an explicit re-entry prompt. These were not chosen because the finding is specifically about a credential in browser storage, and the in-memory approach is the minimal change that removes the storage while the suites show no new failures; encryption would add key-management complexity without removing the stored secret, and a session cookie still persists across some navigations.
