Governed autonomous software development

A fleet of coding agents you can leave running.

Point it at a git repository with a test suite. It works the failing tests in isolated worktrees, keeps only what the test runner proves, and parks a reviewable diff for you. Your checkout is never written to.

Tests are the oracle. The merge is the gate. The score can never go backwards.

What it cannot do

The safety is structural, not behavioural.

None of this depends on the model being well behaved. Each one is a capability the agents simply do not have.

It works elsewhere

Every attempt runs in its own git worktree on its own branch, cut from your last commit. Four agents at once never collide.

Cannot touch your checkout

The runner scores it

A patch is kept only if your test command reports more passing and nothing broken. An agent's account of its own work counts for nothing.

Cannot mark its own homework

The exam is read-only

Tests, conftest.py, runner config, packaging, CI workflows and .git refuse writes — the attempt is wasted, not slipped through.

Cannot weaken the tests

You merge

Finished work parks as a dossier: branch, diff, test delta, risk class. Merging is the one irreversible act, and it is yours.

Cannot push anywhere

Getting started

Python 3.11 and git. No install step.

The builder is standard library only. pip install openai is needed just for OpenAI-compatible endpoints — the Anthropic path runs on urllib.

Get the code

git clone https://github.com/amonxnye/Phoenix.git && cd Phoenix
git checkout claude/software-development-agent-5bv0iw

Prove the machinery before you trust it — no API key needed

Both suites build throwaway repositories with real defects and run the whole system against them using scripted agents. If they pass on your machine, only the model is untested. 

python3 gov/verify_builder.py   # 51/51
python3 gov/verify_campaign.py  # 37/37

Give it a brain

export BRAIN_BASE_URL=https://api.anthropic.com
export BRAIN_API_KEY=sk-ant-...
# or, with `pip install openai`:  export DEEPSEEK_API_KEY=...

Point it at a repository

Start with --limit 1. Nothing can be lost either way, but you want to read its judgement before you trust its volume. 

python3 gov/builder.py run --repo ~/yourrepo \
    --test-cmd "python -m pytest -q" --limit 1

Read the diff, then decide

python3 gov/builder.py gate                # what is waiting, and why
python3 gov/builder.py show    --id 1      # the full diff + test delta
python3 gov/builder.py approve --id 1      # merge into the base branch
python3 gov/builder.py reject  --id 1 --reason "wrong approach"

Rejecting deletes the branch, leaves your base commit exactly where it was, and files your reason as a lesson the next run is handed.

Two ways to work

One agent per test, or a fleet on one problem.

builder run

for a backlog of ordinary failures

Takes each failing test in turn. One agent, a few attempts, and every retry is told what its predecessor did to the suite. Each fix parks separately, so you can approve the good ones and reject the rest. 

python3 gov/builder.py run --repo ~/r \
    --test-cmd "python -m pytest -q"

campaign run

for the one that keeps not working

Sends several agents at the same problem with genuinely different briefs — smallest fix, read the test as a contract, widen the search, rewrite, contrarian. Each round starts from the best result so far and gets stranger as it gets stuck. The whole thing parks as one diff. 

python3 gov/campaign.py run --repo ~/r \
    --agents 4 --rounds 6

The gate

Work arrives as a diff and a measurement.

Whether one agent or twenty-four sorties produced it, the dossier is the same shape — because what a reviewer needs is the same.

$ python3 gov/builder.py gate 1 branch(es) awaiting a human: #1 phoenix/campaign/campaign-1786002513 make 5 failing test(s) pass (campaign/4 agents, 6 attempt(s)) suite 1/6 -> 6/6; green: test_discount_code, test_eta, test_eta_express, test_shipping_express_surcharge, test_shipping_scales_with_weight files: src/orders.py HIGH RISK — money $ python3 gov/builder.py show --id 1 def shipping(weight_kg, express=False): - return 5.0 + base = weight_kg * 1.5 + return base * 2 if express else base def eta_days(distance_km, express=False): - return 99 + return 1 if express else max(1, round(distance_km / 167))

Risk is matched by path, never judged by a model — anything touching auth, secrets, migrations, infrastructure, CI or payments is flagged HIGH, and no amount of silence approves it.

Before you point it somewhere real

What it does not do yet.

  • Needs red tests It only fixes failing tests. A green suite means it does nothing — to hand it a feature, write the failing test first.
  • Python source Your test command can be anything, but the logic that decides which file to edit only considers .py. A JavaScript repository will not work yet.
  • Cost scales A campaign is up to agents × rounds model calls, each carrying a source file and the test output. Try --agents 2 --rounds 3 first.
  • Local merges Approving merges into your base branch. It does not open a pull request, and it never pushes unless you set BUILDER_ALLOW_PUSH=1.
  • Command line The gate and campaigns are CLI-only. The web console still shows the older single-agent workboard.
